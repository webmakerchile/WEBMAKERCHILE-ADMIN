# Scheduled deployments (production cron)

WebMakerLatam runs production cron jobs as **Replit Scheduled Deployments**.
Configure each one from the Deploy tab → "Scheduled" so the job runs in the
same managed environment that owns the secrets.

## Daily DB backup

- **Command**: `./scripts/backup-db.sh`
- **Schedule**: `0 3 * * *` (daily, 03:00 UTC)
- **Required env**:
  - `DATABASE_URL` — already provisioned in the deployment.
- **Off-host destination — pick ONE** (the script accepts both, but at least one is required for a real off-host backup):
  - **Recommended — Google Drive** (uses the existing `google-drive` connector,
    no extra secrets):
    - `BACKUP_DRIVE_FOLDER_ID` — Drive folder ID where dumps are stored.
      Get it from the folder URL:
      `https://drive.google.com/drive/folders/<this-id>`. The connector
      account must have edit access to the folder. Retention is handled by
      the uploader: any `webmaker-*.sql.gz` in that folder older than
      `BACKUP_RETENTION_DAYS` (default 7) is trashed automatically.
  - **Alternative — S3-compatible bucket**:
    - `BACKUP_S3_URI` — e.g. `s3://my-bucket/webmaker/`.
    - `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`.
    - The `aws` CLI must be available in the deployment image. Retention on
      the bucket side should be enforced via the bucket's lifecycle rules.
- **Optional env**:
  - `BACKUP_DIR` — local working dir (default `./backups`). The Scheduled
    Deployment storage is ephemeral, so this only affects the in-run copy.
  - `BACKUP_RETENTION_DAYS` — local + Drive retention in days (default 7).

If neither destination is set the script still produces a local dump but
prints a `WARN: no off-host destination configured` line — treat that as a
configuration error in production.

## Restore (verified manually)

1. Download the most recent `webmaker-YYYYMMDD-HHMMSS.sql.gz` from your
   chosen destination (Drive or S3).
2. Restore into a target Postgres (the same DB or a fresh one):

   ```bash
   gunzip -c webmaker-YYYYMMDD-HHMMSS.sql.gz | psql "$DATABASE_URL"
   ```

   The dump is created with `--clean --if-exists`, so it drops and recreates
   the WebMakerLatam tables before restoring the data. Run against an empty
   DB or one whose contents you intend to overwrite.
3. After restore, boot the API server and hit `GET /api/health` (or run
   `pnpm --filter @workspace/api-server run dev` and load the admin panel)
   to verify the restored schema/data is consistent.

## Verifying the schedule

After saving the Scheduled Deployment, trigger one manual run from the
Deploy tab and confirm the run logs end with `[backup] done`. For Drive,
also confirm the new `webmaker-<ts>.sql.gz` file appears in
`https://drive.google.com/drive/folders/$BACKUP_DRIVE_FOLDER_ID`.
