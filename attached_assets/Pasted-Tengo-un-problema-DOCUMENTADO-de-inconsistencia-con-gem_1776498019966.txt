Documentación oficial relevante:
- Gemini 3 Pro Image Preview tiene un mecanismo de "Thinking" que genera 
  hasta 2 imágenes temporales (bocetos) antes de la final
- El modelo permite máximo 11 imágenes por request (6 object + 5 character)
- Desde el launch de Gemini 3.1 Flash en febrero 2026, el Pro model tiene 
  inconsistencia documentada como bug conocido
- Gemini 3 requiere temperature = 1.0 (default); bajarlo causa degradación
- Para Gemini 3 las instrucciones críticas deben ir AL FINAL del prompt, 
  no al inicio
- El parseo del response DEBE filtrar parts con thought: true y tomar la 
  ÚLTIMA inline_data (no parts[0])

FIX 1 (CRÍTICO - ESTE ES EL MÁS IMPORTANTE): PARSEO DE RESPONSE
═══════════════════════════════════════════════════════════════

PROBLEMA:
Gemini 3 Pro Image devuelve MÚLTIPLES imágenes en el response: los "bocetos" 
del proceso de thinking + la imagen final. Si el código actual toma 
parts[0] o generatedImages[0], probablemente estamos mostrando un BOCETO 
intermedio y no la imagen final. Esto explicaría por qué a veces sale 
incompleta o de baja calidad.

ACCIÓN:

1. Busca en el código (artifacts/api-server/src/routes/community/) dónde 
   parseamos el response de gemini.models.generateContent o 
   generateImages. Muéstrame ese código actual.

2. Reemplaza el parseo por este patrón:

```javascript
// ❌ INCORRECTO (lo que probablemente tenemos):
// const imageData = response.generatedImages[0].image.imageBytes;
// o
// const imageData = response.candidates[0].content.parts[0].inlineData.data;

// ✅ CORRECTO para Gemini 3 Pro Image:
function extractFinalImage(response) {
  const parts = response.candidates[0].content.parts;
  
  // Filtrar cualquier part con thought: true (son bocetos intermedios)
  const imageParts = parts.filter(part => 
    part.inlineData && !part.thought
  );
  
  if (imageParts.length === 0) {
    throw new Error("No se encontró imagen final en el response");
  }
  
  // Tomar la ÚLTIMA imagen (la final, no los bocetos)
  const finalImage = imageParts[imageParts.length - 1];
  
  return {
    mimeType: finalImage.inlineData.mimeType,
    data: finalImage.inlineData.data,
  };
}
```

3. En la request a Gemini, agrega este parámetro para ahorrar tokens:
```javascript
config: {
  // ...otras configs
  thinkingConfig: {
    includeThoughts: false  // No nos devuelve los bocetos, solo la final
  }
}
```

IMPORTANTE: Aunque includeThoughts sea false, los bocetos siguen 
generándose internamente (es feature del modelo, no se puede desactivar). 
Por eso el filter del punto 2 es necesario de todas formas.

FIX 3 (IMPORTANTE): ORDEN Y ESTRUCTURA DEL ARRAY `parts`
═══════════════════════════════════════════════════════════════

PROBLEMA:
Google recomienda etiquetar cada imagen de referencia con su ROL explícito

del prompt.

Refactoriza la construcción del array `parts` así:

```javascript
function buildGeminiPartsArray({ 
  foxReferenceBase64,      // la imagen master del zorro
  canonReferences,          // array de 2-4 imágenes canon adicionales
  prompt                    // el prompt de texto con instrucciones
}) {
  const parts = [];
  
  // 1️⃣ PRIMERO: Imagen master con rol explícito
  parts.push({ 
    text: "REFERENCE IMAGE 1 (PRIMARY CANON — replicate this character EXACTLY. Match outline weight, fur color, glasses shape, eye size, body proportions):" 
  });
  parts.push({ 
    inlineData: { mimeType: "image/png", data: foxReferenceBase64 }

    });
  });
  
  // 3️⃣ ÚLTIMO: Prompt con instrucciones (al final según doc oficial)
```
